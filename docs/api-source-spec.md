# API 数据源对接格式规范

> 本文是 AI4S-Daily 资讯聚合系统对外部 API 数据源的**统一接入格式约定**。
> 各数据源的负责方按此格式组织返回内容即可，系统侧统一完成去重、LLM 评分、报告编排与推送。
> created: 2026-08-28

## 总体要求

每个 API 数据源返回一个 **JSON 数组**，数组中每个元素是一条内容条目（item）。
字段命名允许与本文不同（系统侧可做映射），但**信息必须齐全**；如能对齐本文字段名则零适配接入。

## 条目字段

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `id` | string | 强烈建议 | 条目在源内的**唯一且不变**标识。用于构造稳定链接与增量游标 |
| `title` | string | **必需** | 条目标题，纯文本（不含 HTML），建议 ≤200 字符 |
| `url` | string | **必需** | 条目的**原始出处链接**（canonical URL）。要求：① 同一内容永远返回同一 URL；② 不含签名/时间戳/跟踪参数（utm_*、token 等）；③ 指向内容本身而非列表页 |
| `content` | string | **必需** | 正文或足够详细的摘要，纯文本或 markdown。系统以此作为 LLM 评分与洞察写作的依据，**内容越完整评分越准**；单条建议 500~4000 字符，超长由系统截断 |
| `published_at` | string | 建议 | 发布时间，ISO 8601 格式（如 `2026-08-28T10:00:00+08:00` 或 `2026-08-28`）。缺失时系统以抓取时间兜底，但会影响时效性判断 |
| `author` | string | 可选 | 作者/机构名 |
| `images` | array | 可选 | 图片 URL 列表（当前系统不使用，预留） |

## 返回示例

```json
[
  {
    "id": "item-20260828-001",
    "title": "示例：某某模型发布",
    "url": "https://example.com/news/item-20260828-001",
    "content": "正文内容……（500~4000 字符的完整正文或详细摘要）",
    "published_at": "2026-08-28T09:30:00+08:00",
    "author": "某某实验室"
  }
]
```

## 接口层面的建议（非强制）

以下能力有则更好，没有也能接入：

1. **增量参数**：支持 `since_id` / `updated_after` / `start_date` 之类参数，只返回新内容（系统每小时抓取一次，全量返回会浪费双方资源）；
2. **分页**：`limit` + `offset`/游标，单页上限建议 ≤100 条；
3. **鉴权**：Bearer Token 或自定义 Header 均可，密钥由系统侧通过环境变量配置，不写死在代码里；
4. **限频说明**：告知 QPS / 每日配额即可，系统侧默认每小时一次、单源并发为 1。

## 系统侧行为说明（供负责方理解数据去向）

1. 条目进入管线后按 `url` 做跨天去重与已推送拦截——**URL 稳定性是去重生效的前提**；
2. 每条内容由 LLM 按 AI4S（AI for Science）相关性打分（0-100），≥60 分进入候选池；
3. 高分条目进入每日早报/周报的板块编排（总览、高原/高峰洞察、Top 热点等），报告中署名来源并附 `url` 原文链接；
4. 评分所需的 tags/score/summary 字段由系统侧生成，数据源无需提供。

## 常见问题

- **Q：我们的内容没有公开 URL 怎么办？**
  A：用 `id` 构造一个固定格式的占位 URL（如 `https://example.com/item/{id}`），保证同一条目永远相同即可；若内容日后上线公开页面，再切换到真实 URL（注意切换瞬间旧 URL 会被当作新条目重新推送一次）。
- **Q：content 可以给 HTML 吗？**
  A：可以但建议纯文本/markdown；HTML 会被系统按文本截断，标签会占用有效长度。
- **Q：更新已发布的内容（修订）会重复推送吗？**
  A：只要 URL 不变就不会重复推送；修订内容也不会再次进入报告（已推送记录永久生效）。
